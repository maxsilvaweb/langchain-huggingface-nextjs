--------------------------------------------------------------------------------
1.1 RAG DEEP DIVE: CHUNKING
--------------------------------------------------------------------------------

1.1.1 What is chunking?
> Breaking documents into smaller pieces so vector search can find specific 
  information rather than matching entire documents.

1.1.2 Why 500 characters?
> Sweet spot: small enough to be precise (one topic per chunk), large enough to 
  carry meaningful context; 1000+ mixed topics, 200 lost too much context.

1.1.3 Why 50-char overlap?
> Ensures sentences aren't cut in half at chunk boundaries, so context isn't 
  lost between chunks.

1.1.4 Where is chunking in your app?
> In services.py, the RecursiveTextChunker class uses LangChain's 
  RecursiveCharacterTextSplitter with separators: paragraphs → sentences → words.


--------------------------------------------------------------------------------
1.2 RAG DEEP DIVE: EMBEDDINGS & VECTORS
--------------------------------------------------------------------------------

1.2.1 What are embeddings?
> Numerical vectors (lists of numbers) that represent the meaning of text, so 
  similar meanings are close together in vector space.

1.2.2 One-liner for execs:
> "We turn words into coordinates on a map, so the AI can find related documents 
  by measuring distance."

1.2.3 What are vectors?
> An ordered list of numbers that represents a point in multi-dimensional space.

1.2.4 What are 384-dimensional vectors?
> A list of 384 numbers that together capture the semantic meaning of text, where 
  each dimension represents a learned feature of language.

1.2.5 Why MiniLM-L6-v2?
> Fast, free (HuggingFace API), produces 384-dimensional vectors which keeps 
  storage lean and matches my Convex vector index schema.

1.2.6 Where are embeddings in your app?
> In services.py, the HuggingFaceEmbedder class (with OpenAIEmbedder and 
  GoogleEmbedder fallbacks) generates embeddings via embed() and embed_batch().

1.2.7 Why 384 dimensions?
> All three providers (HuggingFace, OpenAI, Google) output 384 dims so I can 
  switch providers without changing the Convex vector index schema.


--------------------------------------------------------------------------------
1.3 RAG DEEP DIVE: SIMILARITY THRESHOLD
--------------------------------------------------------------------------------

1.3.1 What is the 0.6 similarity threshold?
> Minimum cosine similarity score to include a chunk in the context; anything 
  below 0.6 is considered too irrelevant and filtered out.

1.3.2 How does it work in your app?
> Vector search returns chunks ranked by similarity (0.0 to 1.0); I only inject 
  chunks scoring ≥0.6 into the prompt, preventing noise from diluting the context.

1.3.3 Where is this in your code?
> In constants.py as RETRIEVAL_THRESHOLD = 0.6, used by the ContextRetriever in 
  services.py when filtering retrieved documents.

1.3.4 Why 0.6 specifically?
> Empirically tuned: lower values included irrelevant chunks (noise), higher 
  values filtered out useful context; 0.6 balanced precision and recall.


--------------------------------------------------------------------------------
1.4 DEFINITIONS
--------------------------------------------------------------------------------

1.4.1 What is Polyglot architecture?
> Using multiple programming languages in one system, each chosen for what it 
  does best; in my project, TypeScript handles the UI/auth (Next.js excels here) 
  and Python handles AI orchestration (LangChain's ecosystem is richer in Python).

1.4.2 What does RAG stand for?
> Retrieval-Augmented Generation: instead of relying solely on the LLM's training 
  data, we retrieve relevant documents first, then augment the prompt with that 
  context before the model generates a response.

1.4.3 The RAG Cycle (3 phases):

  Phase            | What Happens                              | My Implementation
  -----------------|-------------------------------------------|------------------------------------------
  R - Retrieval    | Query knowledge base to find chunks       | Vector similarity search in Convex (0.6 threshold)
  A - Augmentation | Inject retrieved context into LLM prompt  | Context block with source names + scores
  G - Generation   | LLM generates grounded response           | LangChain chain with streaming + citations

1.4.4 One-liner for execs:
> "RAG lets the AI answer questions using your company's documents, not just 
  what it learned during training."


--------------------------------------------------------------------------------
1.5 TECHNOLOGY CHOICES: CONVEX
--------------------------------------------------------------------------------

1.5.1 What is Convex?
> A reactive real-time database with built-in vector search; data syncs instantly 
  to all connected clients without polling or WebSockets boilerplate.

1.5.2 How does it scale?
> Convex is a managed serverless platform that auto-scales; I don't provision 
  servers, it handles concurrency, and vector indexes are built-in so no separate 
  Pinecone/Weaviate to manage.

1.5.3 Multi-platform (mobile + web)?
> Both a React Native app and Next.js web app can subscribe to the same Convex 
  queries; when a message is saved, both apps see it instantly without me writing 
  sync logic.

1.5.4 Why not Supabase/Firebase?
> Convex has native vector search (384-dim index built-in) and TypeScript-first 
  schema; Supabase would need pgvector extension, Firebase has no vector support, 
  both require more glue code for real-time.


--------------------------------------------------------------------------------

1.8 ORCHESTRATION
--------------------------------------------------------------------------------

1.8.1 What is orchestration?
> Orchestration is coordinating multiple steps, tools, and LLM calls into a 
  single workflow, like a conductor directing an orchestra.

1.8.2 In the context of my RAG app:
> Orchestration means: receive user message → retrieve relevant docs → build 
  prompt with context → call LLM → stream response → save to database. LangChain 
  handles this chain of steps so I don't wire it manually.

1.8.3 Concrete example from your project:
> In chat.py, LangChain orchestrates: (1) fetching chat history from Convex, 
  (2) retrieving RAG context via the embedder, (3) injecting context into the 
  prompt template, (4) streaming the response from whichever LLM provider is 
  selected, all in one chain.astream() call.

1.8.4 Why orchestration matters:
> Without orchestration, I'd write spaghetti code connecting APIs; with LangChain, 
  I define the chain declaratively and it handles retries, streaming, callbacks, 
  and provider switching.

1.8.5 If they ask about agentic orchestration:
> Agentic orchestration is when the LLM decides which tools to call and in what 
  order (e.g., "search the web, then summarise, then email the user"). My RAG app 
  uses a simpler chain (fixed steps), but LangGraph extends this to agentic loops.

2.3 MCP TOOLS: EXA AND REF IN CURSOR
--------------------------------------------------------------------------------

2.3.1 What are MCPs?
> MCPs (Model Context Protocol) are tool integrations that give the AI access to 
  external data sources. I use two MCPs in Cursor: EXA and REF.

2.3.2 What is EXA (Web Search MCP)?
> EXA gives the AI real-time web search capabilities. Instead of relying on 
  training data (which can be outdated), the AI can search the web for current 
  documentation, recent package updates, or best practices.

2.3.3 Why EXA helps:
> When I'm working with a new library or a recent API change, EXA lets the AI 
  fetch the latest docs rather than hallucinating based on outdated training. 
  Example: "What's the new Next.js 15 caching behaviour?" gets real answers.

2.3.4 What is REF (Documentation Search MCP)?
> REF searches official documentation and reference materials. It's more targeted 
  than general web search, focusing on authoritative sources.

2.3.5 Why REF helps:
> When I need accurate API signatures or framework-specific patterns, REF pulls 
  from official docs rather than Stack Overflow guesses. This reduces 
  hallucinations and gives me code that actually works with current versions.

2.3.6 How they work together:
> REF for "how does this API work?" (official docs), EXA for "what's the 
  community consensus on this pattern?" (broader web). Together, they ground the 
  AI's suggestions in real, current information.

8. HALLUCINATIONS IN AI DEVELOPMENT
================================================================================

8.1.1 What are hallucinations?
> LLM generates plausible-sounding but factually incorrect information not in its 
  training data or provided context.

8.1.2 Why are hallucinations dangerous?
> In legal or journalism, hallucinations cause real harm: wrong advice, 
  misinformation, eroded trust, and liability.

--------------------------------------------------------------------------------
8.2 HOW I TACKLED HALLUCINATIONS AT GRAPPLE LAW
--------------------------------------------------------------------------------

8.2.1 The problem:
> AI giving employment law advice could hallucinate case references, causing 
  users to lose tribunals.

8.2.2 Solution 1 - RAG with verified docs:
> Ingested verified employment law documents so AI only cites from our curated 
  knowledge base.

8.2.3 Solution 2 - Confidence scoring:
> Low-confidence answers triggered disclaimer: "Please verify with a solicitor."

8.2.4 Solution 3 - Human-in-the-loop:
> Users reviewed every AI-drafted ET1 section before submission.

8.2.5 Solution 4 - Uncertainty prompts:
> System prompt instructed AI to say "I don't have information" rather than guess.

8.2.6 Business outcome:
> £70k client wins, Mirror/Observer coverage, zero harmful hallucination incidents.

--------------------------------------------------------------------------------
8.3 HOW I TACKLED HALLUCINATIONS AT BBC NEWS
--------------------------------------------------------------------------------

8.3.1 The problem:
> LLM article rewrites could introduce factual errors; 7,000 journalists needed 
  to trust output.

8.3.2 Solution - Diff-comparison UI:
> Side-by-side diff view let journalists accept/reject individual AI edits.

8.3.3 Why this worked:
> Journalists became the guardrail, catching hallucinations before publication.

--------------------------------------------------------------------------------
8.4 HOW I COMBATED HALLUCINATIONS IN MY TAKE-HOME APP
--------------------------------------------------------------------------------

8.4.1 RAG grounding:
> Responses grounded in retrieved chunks; AI prompted to cite sources as 
  [Source 1], [Source 2].

8.4.2 Similarity threshold filtering:
> Chunks below 0.6 filtered out, preventing irrelevant context causing tangential 
  hallucinations.

8.4.3 Confidence scoring:
> calculate_response_confidence() in guardrails.py triggers disclaimers on low 
  scores.

8.4.4 Uncertainty acknowledgment:
> System prompt: "If context doesn't contain the answer, say so clearly."

8.4.5 Where in code:
> guardrails.py has UNCERTAINTY_PHRASES; llm.py has RAG_SYSTEM_PROMPT with 
  citation instructions.
